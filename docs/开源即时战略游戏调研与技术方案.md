## 1. 项目背景与需求分析

### 1.1 原始需求

> 游戏是即时战斗风格，但操作比较简单；玩家可以选择建造建筑来完成金钱的获取，制造军队，完成对外的战争。

将需求拆解为四个可验证的玩法支柱：

| 支柱 | 玩法含义 | 设计关键词 |
|---|---|---|
| 即时战斗 | 战斗过程实时进行，非回合制 | 实时指令、自动寻路、即时伤害结算 |
| 建造建筑获取金钱 | 经济由建筑驱动，建筑即产出 | 建筑放置、资源产出、建筑升级 |
| 制造军队 | 通过生产建筑持续获得作战单位 | 兵种数据表、生产队列、人口上限 |
| 对外战争 | 主动攻击其他玩家/NPC，掠夺或占领 | 匹配对战、战斗结算、掠夺收益 |

### 1.2 核心玩法循环（Core Loop）

```
                     ┌──────────────────────────────┐
                     │                              │
                     ▼                              │
        建造/升级经济建筑                       战斗胜利
                     │                              │
                     ▼                              │
        持续产出金钱（金币）                     掠夺资源/排名提升
                     │                              │
                     ▼                              │
        在兵营中制造军队（消耗金币+时间）           │
                     │                              │
                     ▼                              │
        编队/出征 → 对外战争（实时战斗）────────────┘
```

即时战斗类策略游戏的乐趣来自"经营节奏 × 战斗爽感"的双循环：玩家离线/挂机时经济建筑持续产金（放置/挂机循环），上线后把积累的金币转化为军队并投入实时战斗（动作循环）。两个循环通过"金币"和"时间"互相约束，构成数值闭环。

### 1.3 系统拆解

| 系统 | 职责 | 复杂度 |
|---|---|---|
| 经济系统 | 金币产出、消耗、存储、数值成长 | 低（配置表驱动） |
| 建造系统 | 建筑放置规则、队列、升级、拆除 | 中 |
| 兵种系统 | 兵种定义、生产、人口、编队、AI 行为 | 中 |
| 战斗系统 | 实时指令、寻路、索敌、伤害结算 | 高 |
| 战争系统 | 匹配、战斗房间、结算、掠夺、战报 | 高 |
| 关卡/AI 系统 | 关卡敌人、波次、NPC 攻城 | 中 |
| 网络系统 | 实时同步、断线重连、反外挂 | 高 |
| 外围系统 | 账号、引导、任务、排行榜、聊天 | 中 |

### 1.4 关键设计决策点

1. **同步模型**：帧同步（lockstep）还是服务器权威状态同步？即时操作 + 简单指令下，服务器权威 + 快照同步更稳、防外挂更好（详见 6.5）。
2. **战斗形态**：异步战报（SLG 常见，非实时）还是实时 PvP？需求明确"即时战斗"，必须做实时 PvP，同时可保留异步战报作为低门槛补充。
3. **平台**：H5/小游戏（获客成本低）还是 PC/手游（表现力强）？影响技术栈（详见 6.2）。

## 2. GitHub 开源项目调研与选型

### 2.1 筛选标准

- **开源协议宽松**：GPL / AGPL / MIT 等，允许商用与二次开发（注意 GPL 传染性，见 8.2）。
- **玩法匹配**：具备"资源采集 → 建造基地 → 生产军队 → 实时战争"完整循环。
- **工程活跃**：近 3 个月内有提交，star 数量与社区规模可观。
- **可参考性**：代码结构清晰、文档齐全、有模组/数据驱动设计，适合作为架构蓝本。

### 2.3 候选项目简评

**Mindustry（主推）**
- 官方定位："The automation tower defense RTS"（自动化塔防 RTS）。
- 玩法与需求高度重合：玩家放置钻头/传送带/工厂等建筑形成资源生产链 → 工厂持续生产机甲/飞船部队 → 实时防守敌人波次或主动进攻敌方基地（战役 Sector 占领、PvP 攻击地图）。
- 操作极简：拖拽放置建筑、点击单位一键编队，单位自动寻路与索敌，完全符合"即时战斗但操作简单"。
- 工程质量顶级：Java + Arc 引擎（libGDX 系），Gradle 多平台工程（core / android / ios / desktop / server / tests），数据驱动的内容系统，ECS 式组件架构，自研 ArcNet 网络库，活跃的模组生态。
- 数据：29.5k stars，最新版本 v160.7（2026-10-08 发布），2026-10-22 仍在提交。

**OpenRA（备选，经典 RTS 范式）**
- 用 C# 重制《命令与征服：红色警戒》等 Westwood 经典游戏的**开源引擎**。
- 完整呈现经典 RTS 循环：采矿车采集矿石 → 建造基地/电厂/兵营 → 生产坦克/步兵 → 与 AI 或玩家实时对战。
- 技术亮点：Trait 特性系统 + MiniYaml 数据驱动的 Mod 体系（Mods.Cnc / Mods.D2k / Mods.Common）、帧同步（lockstep）联机、内置地图编辑器与录像回放。
- 17.6k stars，2026-10-24 活跃。

**OpenFrontIO（Web 端参考）**
- TypeScript 编写、浏览器运行的多人 .io RTS，monorepo 结构（src/client + src/server），AGPL-3.0。
- 如果最终产品是 H5/网页游戏，它的前后端结构、房间模型、部署方式（Dockerfile + nginx + supervisord）直接可参考。

**其他候选落选原因**：Beyond All Reason 与 Zero-K 内容体系庞大、依赖 Spring 引擎，学习成本高于收益；Warzone 2100 操作偏重、3D 渲染管线复杂；Widelands 军事占比低；NetPanzer 理念贴合但项目停滞（近一年仅一次提交）。

### 2.4 选型结论

```
主推参考：Mindustry  → 提供"轻操作 + 建筑经济 + 造兵 + 实时战争"的完整现代范本
备选参考：OpenRA     → 提供"经典 RTS 采集-建造-造兵-战争"循环与帧同步联机范本
Web 参考：OpenFrontIO→ 提供 TypeScript 浏览器 RTS 的工程结构与部署范本
```

三个项目分别覆盖 **玩法蓝本、RTS 机制蓝本、Web 工程蓝本**，下文依次深度解析。

```
Mindustry/
├── core/                 # 跨平台核心代码（游戏逻辑 + 渲染 + 网络）
│   └── src/mindustry/    # 主源码包（详见 3.4）

├── tests/                # 单元测试
```

**借鉴**：逻辑全部放在 `core`，各平台只是壳；`server` 模块直接复用 `core` 跑无头服务器——这正是"客户端/服务端共享同一套游戏逻辑代码"的正确姿势，自研项目应照搬该结构。

### 3.5 核心系统源码级分析

#### 3.5.1 数据驱动内容系统（type/ + content/）

Mindustry 的所有游戏内容都是**类型定义 + 注册表**模式：

- **类型定义（"类"）**：`type/Item.java`、`type/Block.java`、`type/UnitType.java`、`type/Weapon.java` 定义了内容的字段与行为钩子（构造、更新、绘制）。
- **内容注册（"实例"）**：`content/Blocks.java`、`content/UnitTypes.java`、`content/Items.java` 中用链式 API 创建全部实例，例如 `new Item("copper"){{...}}`。
- **消耗器（Consumers）**：`world/consumers/` 下 `ConsumePower`、`ConsumeItems`、`ConsumeLiquid` 等，声明建筑"生产需要消耗什么"，可插拔组合。
- **科技树（TechTree）**：`content/TechTree.java` + `SerpuloTechTree.java` / `ErekirTechTree.java` 定义解锁关系，驱动 UI 研究界面。

> **对自研的启示**：建筑、兵种、子弹、状态效果全部做成"配置表 → 实例"的两层结构，新内容只需加一行注册代码或一条 JSON，不需要改逻辑代码。这正是第 6.6 节数值配置表设计的原型。

#### 3.5.2 建筑/方块系统（world/）

- `world/Block.java`：所有建筑的基类，持有 `size`（占地）、`consumers`（消耗）、`requirements`（建造耗材）、`buildType`（对应 Building 类）等；`Block` 是"类型"，`Building`（`entities/comp/BuildingComp` 及其子类）是"世界中的实例"。
- `world/Tile.java` + `Tiles.java`：网格瓦片，一个建筑可占多格（`size×size`），`Tile` 缓存指向所属 Building 的引用，实现 O(1) 命中查询。
- `world/Build.java`：建造/拆除/配置交互逻辑，配合 `ConstructBlock`（建造中的脚手架状态）。
- 建筑分类目录 `blocks/production`（配方生产）、`blocks/distribution`（传送带物流）、`blocks/power`（电力）、`blocks/units`（工厂）、`blocks/defense`（炮塔）等，直接对应自研游戏的"资源建筑/兵营/防御塔"分类法。

#### 3.5.3 经济系统

- **物品（Item）**：铜、铅、钛、钍、硅、 metaglass、surge alloy、plastanium、phase fabric 等固态资源，通过钻头采集、工厂加工、传送带运输、仓库（核心）存储。
- **液体（Liquid）**：水、矿渣、石油、冷冻液、arkycite 等，管道网络传输。
- **电力（Power）**：`world/blocks/power/` 实现发电机、电池、电网；`PowerGraphUpdaterComp` 组件维护电力图（graph），每个建筑节点按图分配电力——这是典型的**增量图算法**应用（新建筑接入时局部重算，而非全图重算）。
- **生产配方**：`blocks/production/` 下 `GenericCrafter` 等按 `input → output + craftTime` 工作，本质就是"配方表"驱动。

> **对自研的启示**：把"金币产出建筑"抽象为 `产出公式 = f(建筑等级, 加成, 挂机时长)`，服务端离线结算（见 6.4.1）。

#### 3.5.4 军队/单位系统（type/unit + entities/）

- `type/UnitType.java`：单位的"类"定义——武装（`weapons`）、属性（血量/速度/装甲）、行为（`aiController`）、工厂（由哪个工厂生产、耗材、耗时）。
- `type/unit/`：`TankUnitType`（履带/轮式）、`ErekirUnitType`（第二星球单位系）、`MissileUnitType`（导弹单位）、`NeoplasmUnitType`（特殊 AI 单位）。
- `entities/comp/`：**ECS 式组件**，每个组件是单位能力的一个正交维度：
  - `PosComp / VelComp / RotComp`（位置/速度/朝向）
  - `HealthComp`（血量）、`ShieldComp`（护盾）
  - `WeaponsComp`（武器）、`BulletComp`
  - `UnitComp / TeamComp`（单位与阵营）
  - `MinerComp`（采矿行为）、`BuilderComp`（建造行为）、`PayloadComp`（载荷）
  - `LegsComp / TankComp / MechComp`（移动方式：腿/履带/机甲）
  - `UnderwaterMoveComp / ElevationMoveComp`（环境移动）
- `entities/Units.java` + `EntityGroup` + `EntityIndexer`：单位的全局管理、按阵营/类型分组、空间索引（空间哈希网格，用于快速邻域查询）。
- `entities/pattern/`：单位编队走位（编队沿路径保持阵型）。

> **对自研的启示**：兵种 = 组件组合。`步兵 = Pos + Vel + Health + Weapons + Unit`，`骑兵 = 步兵 + Legs + Charge`。用组件化定义兵种，避免类爆炸（详见 6.4.3）。

#### 3.5.5 战斗系统

- `type/Weapon.java` + `type/weapons/`：武器定义（射击间隔、弹道、散射、后坐力动画）。
- `entities/bullet/`：子弹实体（直线/追踪/激光/爆炸弹头），`bullet/BulletComp`、`bullet/BulletType`。
- `entities/Damage.java`：统一伤害入口（支持伤害类型、护甲减免、状态效果）。
- `type/StatusEffect.java`：灼烧/冰冻/感电等状态。
- `ai/`：寻路（flow field 寻路，单位共享势场，适合海量单位）、索敌（`TargetPriority`、`UnitSorts`）。

> flow-field 寻路值得重点关注：RTS 中几百个单位冲向同一目标时，为每个单位单独 A* 开销巨大；Mindustry 用"积分距离场（integration field）+ 方向场"让所有单位共享一次寻路计算，自研游戏海量士兵对冲时应采用同类方案。

#### 3.5.6 AI 与敌人

- `ai/` 包实现敌人波次生成、攻击路径选择、单位 AI（巡逻/追击/撤退）。
- 战役中每个 `Sector`（扇区）有波次规则；`type/Planet.java` / `Sector.java` 定义星图与关卡。

#### 3.5.7 多人网络（net/）

- `net/ArcNetProvider.java`：基于自研 **ArcNet** 库（支持 TCP/UDP、可靠/不可靠包、对象序列化）的网络提供者。
- `net/Packets.java`：全部协议包定义（连接、世界数据流、输入指令、聊天、管理指令）。
- 模型：**服务器权威**——专用服务器（`server/` 模块）运行完整世界逻辑，客户端发送指令、接收快照；`Administration.java` 处理管理指令，`CrashHandler` 处理崩溃上报。
- `net/Streamable.java`：可流式传输的大型数据（地图等）分块传输。

> **对自研的启示**：这正是"即时战斗 + 简单操作"场景下最稳的同步模型——客户端只上报指令（移动/攻击/造兵），服务端验算并广播快照，天然防外挂（详见 6.5）。

#### 3.5.8 UI / 输入 / 模组

- `ui/`：HUD、建造轮盘、对话框、FluentBundle 本地化（`FluentBundle` 多语言）。
- `input/`：键鼠 + 触屏双输入抽象。
- `mod/`：模组系统支持 Java 模组与 JavaScript（Rhino 脚本）模组，可新增内容、覆写行为——证明其数据驱动架构的彻底性。

### 3.6 可借鉴设计模式清单

| 模式 | 在 Mindustry 中的体现 | 用在哪里 |
|---|---|---|
| 类型-实例分离 | `type/*` 定义 + `content/*` 注册 | 建筑表、兵种表、子弹表 |
| ECS 组件化 | `entities/comp/*` | 单位/子弹行为组合 |
| 消耗器插件化 | `world/consumers/*` | 建筑产出消耗规则 |
| 增量图算法 | `PowerGraphUpdaterComp` 电力网 | 服务端离线收益结算 |
| Flow-field 寻路 | `ai/` 距离场 | 海量单位寻路 |
| 服务器权威 | `server/` + `net/ArcNet` | PvP 联机与反外挂 |
| 多平台壳工程 | core/android/ios/desktop/server | 一套代码多端发布 |

- **Trait 系统**：游戏对象（Actor）没有复杂继承树，行为全部由可组合的 Trait 插件拼装（如 `Mobile`（移动）、`Attack`（攻击）、`Production`（生产）、`Harvester`（采集）、`Building`（建筑））。这与 Mindustry 的组件系统同构，是 RTS 架构的"标准答案"。
- **MiniYaml 数据驱动**：所有单位、建筑、武器、规则都在模组的 `.yaml` 文件中声明，引擎读取 `FieldLoader` 反射填充——改内容不改代码。
- **帧同步联机**：`Sync.cs` + `Orders/` 实现 lockstep：所有客户端每帧上传指令，同一帧号统一执行；`Network/` 下的 GSP（Game Sync Protocol）处理握手、同步、延迟补偿、录像回放。
- **模组体系**：`Mods.Cnc` 等模组 = YAML 规则 + 资源包，社区可自建新游戏。

### 4.3 借鉴点

1. **采集-建造-造兵-战争经典循环**的最完整开源实现（矿车/电厂/兵营/坦克厂/雷达/超级武器）。

4. YAML 内容管线的组织方式（目录即命名空间）。

## 6. 自研游戏技术方案

> 以下为综合上述三个参考项目后，针对"即时战斗 + 建筑经济 + 造兵 + 对外战争"的落地方案。示例数值均为设计建议值，需实测调优。

### 6.1 玩法框架

- **双循环结构**：
  - 经营循环（离线/挂机）：经济建筑按时间产出金币 → 升级建筑提升产出 → 金币累积。
  - 战斗循环（在线/实时）：金币 → 兵营造兵（实时生产队列）→ 编队出征 → 实时 PvP/攻城 → 掠夺收益反哺经营。
- **对外战争三种形态**（按开发优先级）：
  1. **攻城掠夺（异步战报）**：低门槛，服务端模拟结算，适合 MVP。
  2. **实时 PvP**：核心卖点，双方实时带兵对冲。
  3. **关卡/NPC 攻城**：AI 敌人定时来犯，检验防守布防。

### 6.2 技术栈选型

| 路线 | 技术栈 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| A. Web/H5 | TypeScript + Cocos Creator 3.x（或 Phaser 3）+ Node.js(Colyseus/Nest) + Redis + MySQL | 获客成本低、即点即玩、可发小游戏 | 实时性能上限、包体限制 | 目标为网页/小游戏 |
| B. 桌面/Steam | Java + libGDX/Arc（同 Mindustry）或 Godot 4 + 自研服务端 | 性能强、可商业化买断、参考项目代码可直接读 | 开发门槛高、获客靠平台 | 目标 PC/Steam |
| C. 手游 | Unity 3D + C# 服务端（.NET）或 Godot | 表现力强、商业化成熟 | 成本高、周期长 | 有成熟团队/预算 |

**推荐**：若团队以 Web 技术为主，选 **路线 A（Cocos Creator + TypeScript 全栈）**，服务端框架参考 OpenFrontIO 的房间模型，同步模型借鉴 Mindustry 的服务器权威设计；若追求长期可维护且愿意深入阅读参考代码，选 **路线 B**。

### 6.3 总体架构

设计原则（全部来自参考项目）：
1. **逻辑与表现分离**：`core` 逻辑层可在客户端与服务端复用（Mindustry 模式）。
2. **服务器权威**：金币、伤害、掠夺结果一律服务端结算（Mindustry/OpenFrontIO 模式）。
3. **数据驱动**：建筑、兵种、武器全部走配置表（Mindustry/OpenRA 模式）。
4. **房间制**：每场战斗独立房间，战斗结束即销毁，经营数据常驻（OpenFrontIO 模式）。

### 6.4 核心系统设计

#### 6.4.1 经济系统

**金币产出公式**（服务端离线结算，参照电力网增量思想）：

```
离线收益 = Σ(每座产出建筑 基础产量 × 等级系数 × 时长(小时, 上限8h))
```

- 产出建筑示例表：

| 建筑 | 基础产量 | 升级消耗 | 解锁条件 |
|---|---|---|---|
| 金矿 Lv1 | 60 金/小时 | 200 金 | 初始 |
| 金矿 Lv2 | 120 金/小时 | 800 金 | 主城 Lv2 |
| 金矿 Lv3 | 240 金/小时 | 3000 金 | 主城 Lv4 |
| 金库（提升掠夺保护） | — | 1500 金 | 主城 Lv3 |
| 磨坊（产粮，养兵人口） | 20 粮/小时 | 500 金 | 主城 Lv2 |

- 防挂机垄断：离线收益时长上限 8 小时；在线时收益 ×1.2。
- 所有产出类数值走配置表（见 6.6），支持热更新。

#### 6.4.2 建造系统

- **网格化放置**：基地为 N×M 网格（如 20×20），建筑占 1×1 / 2×2 / 3×3。
- **放置规则**：地形可行走、不重叠、道路连通（金矿需毗邻道路）、前置解锁满足。
- **建造队列**：点击放置 → 进入"建造中"状态（倒计时或立即完成）→ 完成生效；升级为"保留等级、重置功能"或"原地叠加"，建议采用**升级不重置**。
- **数据**：`building_instance` 表存每座建筑的类型/坐标/等级/状态。

#### 6.4.3 兵种系统（组件化，参照 Mindustry comp）

```
兵种定义 = 组件组合 + 数值参数
步兵  = Pos + Move(ground) + Health + Weapon(melee) + Formation
弓手  = 步兵 + Weapon(ranged, projectile)
骑兵  = 步兵 + Move(charge) + Health×2.5 + Weapon×1.8
攻城车 = Pos + Move(siege) + Health×6 + Weapon(building_bonus)
```

- 兵种配置表字段：`id, name, cost{coin,time}, hp, atk, atk_speed, move_speed, range, population, counter{}, countered_by{}`
- **生产**：兵营（步兵/弓手）、马厩（骑兵）、工坊（攻城车）；每兵种独立队列，支持"金币加速"。
- **人口**：磨坊/民居提供人口上限，超限无法生产。
- **克制链**：步兵克弓手、弓手克骑兵、骑兵克步兵、攻城车克建筑——简单三角克制保证"操作简单"下仍有策略深度。

#### 6.4.4 即时战斗系统

- **指令集**（保持简单）：`移动(x,y)`、`攻击(目标id)`、`驻防(建筑id)`、`撤退`。单位自动寻路 + 自动索敌（进入射程且仇恨范围内）。
- **寻路**：小规模（<100 单位）A* 网格寻路；大规模对冲采用 **flow-field**（参考 Mindustry 的 `ai/` 距离场），多单位共享一次寻路。
- **战斗数值**：`伤害 = max(基础攻击 × 数量, 1) × 克制系数(1.5) / 装甲减免`，服务端按 10 TPS（每秒 10 个逻辑 tick）结算。
- **客户端表现**：逻辑 tick 快照 + 插值（lerp）平滑到 60 FPS；受击/死亡播特效；提供 2 倍速与"跳过战斗看结果"（异步战报模式）。

#### 6.4.5 对外战争系统

- **实时 PvP 流程**：
  1. 玩家编队（最多 5 队，每队上限 200 人口）→ 点击"出征"。
  2. 匹配服务按**战力值**（Σ 兵种造价×系数）±15% 匹配对手。
  3. 双方进入战斗房间：进攻方带兵，防守方为**防守镜像**（服务端按防守方布防生成的 AI 布防），3 分钟限时。
  4. 胜负条件：摧毁防守方主基地 50% 耐久 → 进攻胜；超时 → 防守胜。
  5. 结算：进攻胜 → 掠夺防守方**可掠夺金库的 30%**（受金库等级保护上限）；防守胜 → 获得荣誉点。
- **反碾压**：匹配区间 + 战力差补偿（弱势方防御建筑伤害 +10%）。
- **战报回放**：房间全程录制指令序列（帧同步思路），客户端可回放（OpenRA 的录像机制）。
- **异步攻城（MVP 降级方案）**：服务端批量模拟（类 Mindustry 波次结算），产出文字战报，后续升级为实时。

#### 6.4.6 AI 系统

- **关卡/NPC**：定时波次进攻玩家基地（Waves 模式，参照 Mindustry Sector 波次规则），波次表配置化：`wave, units[], count, interval`。
- **防守方镜像 AI**：把防守方建筑与守军交给行为树 AI 控制（巡逻→索敌→集火→补建筑）。
- **难度曲线**：前 10 波线性，第 10 波后按玩家战力动态缩放（Dynamic Difficulty）。

#### 6.4.7 任务与成长

- 主线任务（建造第一个金矿、造出第一支步兵队、赢得第一场战争）。
- 日常任务（产出 X 金、胜利 N 场、掠夺 X 金）。
- 成长线：主城等级 → 解锁建筑/兵种/人口 → 战力提升 → 匹配更强对手。

### 6.5 网络同步方案

| 模型 | 原理 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| 帧同步 lockstep | 所有客户端同帧执行指令（OpenRA） | 带宽极小、易回放 | 任一人掉线卡全场、防作弊差 | 不采用 |
| **服务器权威状态同步** | 客户端上报指令，服务端算状态广播快照（Mindustry） | 防外挂强、掉线可重连快照 | 带宽略大、服务端算力成本 | **采用** |
| 异步战报 | 服务端一次性模拟 | 零实时成本 | 无操作感 | 作为 MVP 补充 |

**实现要点**：
- 逻辑 10 TPS，快照协议：`{tick, units:[{id,x,y,hp,state}], bullets:[...]}`，只广播视野内（AOI 九宫格）实体。
- 客户端指令上行：移动/攻击/技能，带 tick 号；服务端校验合法性（距离、CD、资源）。
- 断线重连：服务端重发全量快照 + 客户端状态重置。
- 传输：WebSocket（H5）或 TCP/KCP（客户端游戏），消息用 JSON（开发期）→ Protobuf（上线期）。

### 6.6 数值配置表设计

```json
  "name": "金矿",
```

### 6.10 性能优化与反外挂

**性能**：
- 单位渲染：同兵种合批（instancing / 图集批合并）。
- 寻路：flow-field 共享计算；远距离单位分批寻路。
- 网络：AOI 裁剪 + 增量快照（只发变化字段）+ 二进制协议。
- 服务端：房间分帧（每房间独立 tick，错峰执行）；Redis 缓存热点数据。

**反外挂**：
1. 全服务器权威结算，客户端无经济/伤害最终权。
2. 指令频次与合法性校验（移动速度上限、攻击 CD、资源足够性）。
3. 战斗房间录像留存，支持追溯与举报复核。
4. 敏感操作（充值、掠夺）二次校验与对账。
5. 通信加密（TLS/WSS）+ 协议版本号防重放。

## 8. 风险与注意事项

### 8.1 技术风险
- **实时同步复杂度**：M2 阶段是最容易失控的部分，务必先用"异步战报"上线验证玩法，再迭代实时 PvP。
- **海量单位性能**：同屏 200+ 单位时需提前做合批与寻路优化（flow-field），不要等问题出现再重构。
- **平衡性**：克制链与掠夺比例需要长期数据调优，配置表化是前提。

### 8.2 开源协议风险（重要）
- Mindustry、OpenRA 为 **GPL-3.0**：直接复制/修改其代码并分发（包括发布可执行文件）时，你的衍生作品也须以 GPL-3.0 开源；网络部署（SaaS）GPL-3.0 **不触发**开源义务，但 AGPL-3.0（OpenFrontIO）**会触发**。
- **建议**：仅将上述项目作为**架构与机制学习参考**，自研代码独立编写；直接搬代码前咨询法务。美术/音频/地图资产同样受协议与版权约束，切勿直接商用。

### 8.3 设计风险
- "操作简单"与"策略深度"需平衡：克制链 + 编队 + 兵种组合是低成本解法。
- 对外战争的掠夺比例直接决定生态：过高打击防守方体验，过低进攻方无动力，建议 25%-35% 并加保护上限。
